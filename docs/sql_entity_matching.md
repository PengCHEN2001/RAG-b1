# SQL 实体匹配：首版行为约定

以下规则和用例用于逐步实施实体匹配。用例通过公开的 `retrieve_sql()` 入口运行，
使用临时 SQLite 数据库和固定的模拟模型输出，不调用线上模型，也不读取业务数据库。
测试中的单位、阵营和来源取自当前数据库的小型子集，并保留相似名称作为干扰项。
能力用例保留关键名称与卡片行定位信息，规则文本使用测试占位内容。
这些用例验证匹配行为，不衡量模型提取名称、判断实体类型的准确率。

## 匹配规则

1. 模型提取原始名称或 ID 片段；应用负责匹配数据库身份。
2. ID 按字符串精确匹配，保留前导零，不补零、不做模糊纠正。
   目录能力使用真实 ID 及所属阵营；卡片能力使用 `unit_id + line`，没有目录 ID 时不生成替代 ID。
3. 名称使用 Unicode NFKC、大小写和空白规范化；保留原始片段与数据库规范名称。
   首版不做翻译、单复数推断或通用标点删除。
4. 完整名称的精确匹配优先于省略匹配和拼写相似度。
5. 已明确实体类型及上下文时，完整词或连续短语的省略匹配只有一个身份才可直接解析。
   名称相同但 ID 不同的记录保留为不同候选，不按名称合并。
6. 拼写近似匹配首版只提供最多五个候选，不自动选定，即使第一名明显领先。
   使用标准库 `difflib.get_close_matches` 的 0.6 分数下限召回建议，不在验收用例中固定分数；
   这个分数不是正确概率，自动接受阈值留待独立样本验证。
7. 明确的阵营与来源是约束。约束下没有候选时要求澄清，不静默扩大搜索范围。
   阵营与来源先解析，其次是单位，最后是能力等实体。单位支持阵营与来源；
   卡片能力支持所属单位及其阵营、来源；其他带阵营外键的实体支持阵营约束。
   实体可以用可选的 `faction_key`、`source_key`、`unit_key` 引用同一请求中对应上下文实体的 key，
   使用不带 `@` 的 key；明确引用的上下文只约束引用它的实体。
   单个未被引用的上下文作为共享条件，多个未被引用的同类上下文需要先澄清适用关系。
   能力声明的可选 `line` 必须由问题明确提供，同时指定 `unit_key`。
8. 多个合理身份要求澄清，候选展示规范名称、真实身份、阵营及可用来源。
   同时保留 `matched_text` 原始片段与 `match_type`（`id` / `exact` / `phrase` / `fuzzy`）。
   没有足够接近的候选时返回空候选的澄清结果。
9. 澄清结果不执行最终业务查询，不返回业务数据。

名称搜索扫描当前类型及适用上下文约束下的完整词表，不受业务查询的 200 行上限限制。
SQL 读取仍保留执行器的字节、时间及 VM 步数预算；词表因预算截断时要求收窄实体上下文，
不使用部分词表判定匹配。精确及短语匹配最多展示 200 个候选，错拼建议最多展示 5 个；
省略的候选通过 `truncated` 标记。首版逐次扫描小型词表，性能需要时再增加索引。

## 能力身份与查询交接

能力词表合并 `abilities` 与 `datasheets_abilities`。全局名称搜索包含目录名称及卡片上
非空的专属名称；限定所属单位或来源时，也包含从目录继承名称的卡片条目。
卡片名称优先于目录名称，卡片规则文本同样保留覆盖关系。
目录中空阵营的核心能力适用于各阵营；卡片条目始终受所属单位的实际阵营和来源约束。

`Might is Right` 没有目录能力 ID。在测试及当前真实数据库中，Warboss 和
Warboss In Mega Armour 各有一条同名记录，因此单独查询名称会要求澄清。
限定 Warboss 后，用 `unit_id=000000001`、`line=3` 定位，保留这两个真实字段。
若同一单位上存在多个同名条目，可同时提供单位和卡片行号。

SQL 生成接收 `required_bindings`：目录身份使用 `<key>_id`，目录能力还使用
`<key>_faction_id`（核心能力为 `""`）；卡片能力使用 `<key>_unit_id` 与 `<key>_line`。
应用先检查这些绑定的值保持不变，再验证实际 SQL 的身份条件。

固定查询通过 `functions.build_fixed_query()` 共用注册函数的参数校验；旧 JSON 入口
`parse_function_call()` 只负责解码与选择结构检查。内部 SQL builders 接收已验证参数，
不重复检查字符串。固定路径的实体声明只在新增字面 ID 声明时再次校验。

## 生成 SQL 的身份约束与修复

`constraints.validate_entity_constraints()` 使用 SQLGlot 的 SQLite AST 与作用域，
只负责实体身份条件；SQLite 执行器独立负责编译、权限及资源限制。

- 身份参数必须直接与对应主键或已知关联键比较，出现在 `WHERE` 或内连接的 `ON` 中。
  支持正反顺序的等号、`AND`，以及两条 `OR` 分支均保留的相同约束。
- 多个已解析的单字段身份可使用 `IN (:first_id, :second_id)`；列表不能夹入字面值、
  未解析参数或复合身份。跨不同身份的 `OR` 需改写为 `IN` 或分别使用表别名。
- 卡片能力的单位和行号必须约束同一 `datasheets_abilities` 别名；目录能力的 ID 和阵营
  必须约束同一 `abilities` 别名，避免匹配跨阵营的同 ID 记录。
- 实际作为必需输入的 CTE/派生表可以传递其内部约束；集合操作每个分支都要保留约束。
  投影、字符串、注释、标量子查询、未使用的 CTE、未关联的 `EXISTS` 及可选左连接的
  `ON` 条件均不能充当身份筛选。含实体的查询不接受 `RIGHT` / `FULL JOIN`。
- 不可证明的 SQL 形式返回 `sql_policy`，不尝试自动修复。此检查不证明任意 JOIN、
  投影、数值计算或自然语言意图的整体语义；这些仍需结果评估。

语法或名称解析失败仍最多修复一次。修复输入保留原问题、已解析身份和必需绑定，
并传入 `repair.sql`、`repair.parameters`、错误代码及有长度限制的诊断，
不发送数据库结果行。修复后的 SQL 重新经过同样的身份约束和执行检查；
权限、参数、执行预算失败与空结果不重试。
